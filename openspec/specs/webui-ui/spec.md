# webui-ui Specification

## Purpose
定义 appkeeper Web 控制台必须呈现的界面元素与行为：左侧两层菜单树
（注册应用 app → 其下进程）承载导航，主区展示选中对象的进程信息与日志，
把各应用的程序及其实时运行状态、控制操作可视化。作为后续前端与 API 实现变更
的统一验收依据。（2026-09-05 修订：对齐 app-registry 能力——第一层为注册应用，
不再是单一实例。）

## Requirements

### Requirement: 左侧两层导航

控制台 SHALL 在左侧提供两层菜单树：第一层为 app 节点，代表一个注册的应用
（app-registry 能力，`ak compose` 的注册记录）；第二层为该应用配置声明的
全部程序，以程序名展示。树 MUST 覆盖全部已注册应用的全部程序，包括尚未启动
过的程序。选中 app 节点时主区展示 App 概况；选中某个程序时主区展示该程序的
进程详情与日志；页面 SHALL 另有守护进程概况的展示位置（覆盖全部应用）。
应用名与程序名 SHALL 单行显示、超宽时省略并保留完整名称提示；程序名文字
SHALL 保持中性色，状态只通过行首指示点与可访问名称表达。

#### Scenario: 树中可见全部程序

- **WHEN** 注册了 2 个应用、共声明 3 个程序且 Web 控制台加载完成
- **THEN** 侧栏树按应用分组列出全部 3 个程序名

#### Scenario: 未启动的程序可见

- **WHEN** 某程序已声明但尚未被启动过
- **THEN** 它仍出现在树中，选中后其详情里 PID 与 uptime 显示为空/占位而非报错

#### Scenario: 选中驱动主区

- **WHEN** 用户在树中点选 app 节点或某个程序
- **THEN** 主区切换为对应的 App 概况或进程详情，当前选中项在树中有可感知的
  高亮标识

#### Scenario: 长名称不破坏树形

- **WHEN** 某个应用名或程序名超过侧栏可用宽度
- **THEN** 该节点保持单行并与短名称行高一致，名称省略显示且可悬停查看全名，同级节点
  不再因它整体错位

### Requirement: App 概况

选中 app 节点时，主区 SHALL 展示两层内容：其一为该应用的概况（应用名、
程序数）；其二为该应用全部程序的状态汇总——以表格列出每个程序的名称、当前状态、
重启计数与 uptime，并提供进入各程序详情的入口。汇总表 SHALL 同时展示 CPU、内存与
日志速率列，未运行程序显示占位。表格标题栏 SHALL 承载该表的日志速率窗口切换；
应用级 apply 与应用级危险操作（移除应用）SHALL 位于页面标题区的操作区。
守护进程概况（配置来源、巡检间隔 monitor_interval、守护进程运行时长）SHALL
在页面级展示，覆盖全部应用。

#### Scenario: 概况可读

- **WHEN** 控制台加载完成且后端可达
- **THEN** 页面展示配置来源、monitor_interval、守护进程 uptime；选中 app 节点
  时主区展示该应用全部程序的状态汇总表

#### Scenario: fatal 程序在汇总中醒目

- **WHEN** 某程序进入 fatal
- **THEN** App 概况的汇总表以警示样式标注该行，页面存在可感知的汇总提示

#### Scenario: 速率窗口跟随表格

- **WHEN** 用户在 App 概况改变日志速率窗口
- **THEN** 切换控件位于程序表标题栏，改变后该表全部速率列立即按新窗口显示

### Requirement: 进程详情

选中某个程序时，主区 SHALL 以单列信息流展示：标题行（含所属应用、程序名、状态徽章与
start/stop/restart 操作）→ 紧凑指标条（PID、uptime、退出/重启次数、CPU、内存、健康状态）
→ 命令行文本块（命令 + args，等宽字体，含工作目录）→ stdout 与 stderr 日志查看器。
日志查看器 SHALL 占据该页剩余可用高度，而不是被上方信息块挤压成固定矮块。

#### Scenario: 展示运行信息

- **WHEN** 用户在树中选中一个程序
- **THEN** 主区呈现该程序的命令行、状态徽章、PID、uptime 与重启计数

#### Scenario: 日志占满剩余高度

- **WHEN** 在 900px 高的视口中打开一个运行中程序的详情
- **THEN** 日志查看器填满信息块以下的剩余高度，页面本身无需纵向滚动即可看到日志区

### Requirement: 状态展示

控制台 SHALL 用可区分的状态指示呈现每个程序的生命周期状态，至少覆盖：
`running`（运行中）、`backoff`（退避中）、`exited`（已退出）、`fatal`（故障）。
App 概况汇总与进程详情 SHALL 渲染完整状态徽章（指示点 + 形状 + 中文状态词）；
侧栏树 SHALL 以状态指示点 + 可访问名称表达同一状态。三处的状态词表与色板 MUST
一致，且 MUST 通过形状与文字同时区分，不得仅靠颜色。不认识的 slug SHALL
原样显示，不得渲染为空。

#### Scenario: backoff 状态可见

- **WHEN** 某程序退出且处于退避等待期
- **THEN** 该程序的状态徽章显示「退避中」及剩余/下次重启的退避秒数

#### Scenario: fatal 状态醒目

- **WHEN** 某程序连续重启次数耗尽进入 fatal
- **THEN** 该程序在树中、汇总表与详情页的状态呈现均以警示样式呈现，并显示「故障」

#### Scenario: 徽章真实渲染

- **WHEN** 控制台加载完成并展示任意程序
- **THEN** App 概况「状态」列与进程详情标题旁均可见带文字的状态徽章，不出现空白状态列

### Requirement: 单程序控制

进程详情 SHALL 通过统一「程序操作菜单」对每个程序提供 stop 与 restart 操作，并对处于
非 running 状态且允许启动的程序提供 start 操作：详情页头部提供 ⋯ 触发按钮，页面任意处
右键亦可打开同一菜单（菜单语义、配色、确认与反馈见「程序操作菜单」）。破坏性操作
（stop / restart 运行中的程序）MUST 经菜单内联确认步骤后才会生效；start 选中即执行。
操作结果 MUST 以可见的反馈呈现（成功 / 失败原因）。进程详情页 MUST NOT 再渲染常驻的
start/stop/restart 按钮组。

#### Scenario: 重启运行中的程序

- **WHEN** 用户对 running 状态的程序经菜单选择 restart 并确认
- **THEN** 后端执行重启流程，界面上该程序状态经 backoff/starting 过渡后回到 running

#### Scenario: 停止操作需确认

- **WHEN** 用户经菜单选择运行中程序的 stop
- **THEN** 出现内联确认步骤；确认前不产生任何状态变更

#### Scenario: 操作失败有反馈

- **WHEN** 控制请求被后端拒绝（如程序已处于 fatal 且不允许 start）
- **THEN** 界面展示失败原因，而不是静默无反应

### Requirement: 日志查看

进程详情 SHALL 内嵌该程序 stdout 与 stderr 日志的查看器：默认展示文件末尾的
最新内容（tail），提供"跟随"开关（开启后持续追加新内容，关闭后停留在当前
视图），并提供暂停跟随时的手动刷新手段。日志 MUST 以等宽字体、保留换行的
只读文本呈现，stdout 与 stderr 可区分。

查看器 SHALL 提供日志配色档位选择器（位于查看器工具栏）：终端黑（缺省，黑底白字）、
纸面白（白底黑字）、米黄（护眼，`#F2EDDF` 底 `#4A4234` 字）三档，档位定义与
stderr 着色约束见 `webui-visual-system`「日志窗口配色档位」。所选档位 SHALL 经
浏览器本地存储持久化，缺省为终端黑；切换 MUST 即时生效，MUST NOT 跟随应用明暗主题。

日志区无输出时 MUST NOT 渲染任何等待类占位文案（如「等待输出…」）；工具栏的行数
计数不受影响。

#### Scenario: 查看最新日志

- **WHEN** 用户选中某程序查看其日志
- **THEN** 展示该日志文件的末尾片段，而非要求从文件头翻阅

#### Scenario: 跟随新输出

- **WHEN** 跟随开关开启且程序持续输出
- **THEN** 新日志行持续追加并保持视口贴近最新内容；用户向上翻阅历史时跟随应
  让位于浏览（不强行拉回底部）

#### Scenario: 缺省黑底白字

- **WHEN** 用户首次打开日志查看器（本地无历史选择）
- **THEN** 日志区以终端黑档呈现（黑底白字），无论应用当前处于明色或暗色主题

#### Scenario: 档位切换即时生效且持久

- **WHEN** 用户把档位从终端黑切到米黄，随后刷新页面
- **THEN** 切换即时生效且 stderr 行仍以红色系区分；刷新后仍为米黄档

#### Scenario: 空输出无占位文案

- **WHEN** 选中一个尚未产生任何输出的程序
- **THEN** 日志区不出现「等待输出…」等占位文案；工具栏行数计数显示 0

### Requirement: 状态实时刷新
侧栏树、App 概况与进程详情中的程序状态、重启计数 SHALL 实时刷新：后端通过
WebSocket 推送变更；WebSocket 不可用时 MUST 自动回退为周期性轮询，且在恢复后
回到推送模式。刷新过程不得打断用户正在进行的交互（如翻阅日志）。

#### Scenario: 状态变化即时可见
- **WHEN** 某程序在守护循环中由 running 变为 backoff
- **THEN** 打开中的控制台无需手动刷新即可在树中与详情页看到状态徽章更新

#### Scenario: WebSocket 断开回退轮询
- **WHEN** WebSocket 连接断开
- **THEN** 界面改用轮询继续刷新数据，并给出"实时连接已断开"的可见提示

### Requirement: 后端不可达降级
当后端 API 不可达或请求失败时，控制台 SHALL 展示明确的离线/错误状态（横幅或
等效提示），保留最后成功加载的数据并标注其过期，而不是渲染空白页或抛出未处理
错误。后端恢复后控制台 MUST 自动回到正常展示，无需用户手动刷新页面。

#### Scenario: 后端离线提示
- **WHEN** 后端进程退出后用户刷新控制台页面
- **THEN** 页面渲染出离线提示与最后已知数据（标注过期），而非空白或报错堆栈

#### Scenario: 后端恢复自动复原
- **WHEN** 后端重新启动且 API 恢复可用
- **THEN** 控制台自动恢复实时数据展示，离线提示消失

### Requirement: pending 变更提示与 apply 操作

控制台 SHALL 呈现待应用（pending）配置变更：存在 pending 时界面 SHALL 有
全局可见的提示（徽章/横幅），并在 App 概况与进程详情中标明哪些程序配置有
变化。SHALL 提供 apply 操作：全局 apply（应用全部）、App 级 apply（仅该
app，附范围说明）、`--restart` 开关（对无变更程序也重启，语义与 CLI 一致）。
apply 为变更生效动作，MUST 经过确认步骤。apply 结果 SHALL 以简洁清单/通知
呈现，逐程序标明配置变化与执行动作（重启 / 仅更新定义 / 保持停止 / 未动），
使用户无需比对配置即可分辨发生了什么。apply 完成后 pending 提示 SHALL
消失（应用失败被隔离的 app 除外）。

#### Scenario: pending 徽章出现

- **WHEN** 用户编辑了某 app 的配置使磁盘与运行状态出现差异
- **THEN** 界面出现全局 pending 提示，相关程序的行上有变更标记

#### Scenario: App 级 apply 不波及其他

- **WHEN** 两个 app 均有 pending，用户在 App A 概况执行 apply（不带 restart）
- **THEN** 仅 A 的变更被应用；B 的 pending 提示保留，B 的程序不受影响

#### Scenario: apply 结果可读

- **WHEN** 全局 apply 完成，范围内含「配置有变且在跑」「配置有变但停止」
  「无变化」三种程序
- **THEN** 结果呈现逐程序区分三类动作，pending 提示消失

#### Scenario: apply 失败有反馈

- **WHEN** apply 请求被后端拒绝或部分 app 应用失败
- **THEN** 界面展示失败原因与受影响范围，成功的部分不被回滚显示

### Requirement: 资源利用率与日志速率展示

控制台的程序列表（App 概况汇总表与进程详情）SHALL 为每个程序展示：

- CPU 利用率（百分比）与内存（人性化单位，如 MiB），程序未运行时显示
  占位（如 `--`）而非 0；
- 日志输出速率（行/秒），stdout 与 stderr 可区分或可切换；速率窗口 SHALL
  可在 1s / 10s / 1min / 5min 之间切换，缺省 10s，切换即时对全部列表生效。

守护进程概况 SHALL 展示系统级 CPU 与内存（已用/总量）。

#### Scenario: 列表含指标列

- **WHEN** 至少一个程序运行中且控制台完成一次数据刷新
- **THEN** 列表中该程序行展示 CPU 百分比、人性化内存与日志速率列，
  未运行程序相应列为占位

#### Scenario: 速率窗口切换

- **WHEN** 用户把日志速率窗口从 10s 切换到 1min
- **THEN** 全部程序的速率列立即按 1min 窗口重新显示

#### Scenario: 系统概况可见

- **WHEN** 控制台加载完成且后端可达
- **THEN** 页面级概况含系统 CPU 与内存使用情况

### Requirement: 刷新频率控制

控制台 SHALL 提供状态/指标显示的刷新频率选择：1s / 3s / 5s / 10s，缺省
3s。所选频率 SHALL 持久化（localStorage），重新打开页面后保留。该节流
MUST 只作用于列表与指标的显示更新节奏，MUST NOT 影响日志跟随流的实时
推送与渲染。

#### Scenario: 切换刷新频率生效

- **WHEN** 用户把刷新频率从 3s 切到 10s
- **THEN** 列表与指标随后按 10s 节奏更新，期间不出现中间刷新

#### Scenario: 偏好持久化

- **WHEN** 用户选择 5s 后关闭页面再次打开
- **THEN** 刷新频率默认回到 5s

#### Scenario: 日志跟随不受节流

- **WHEN** 刷新频率设为 10s 且某程序日志持续输出、查看器处于跟随状态
- **THEN** 日志内容仍实时滚动追加，不受 10s 节流限制

### Requirement: 高速日志降级显示

日志查看器 SHALL 优雅应对高速输出（目标 10MB/s 量级）：

- 后端丢弃批次时插入的「跳过 N 行」标记 SHALL 以可区分的样式（非普通
  日志行外观）显示，N 为丢弃行数；
- 查看器在浏览器内存中保留的日志行数/字节数 MUST 有界，超出时丢弃最旧
  内容，不随输出无限增长；
- 渲染 MUST 批量节流（不逐行触发 DOM 更新）；用户向上翻阅历史时，持续
  的高流量输出 MUST NOT 把视口强行拉回底部或冻结页面。

#### Scenario: 丢行标记可见

- **WHEN** 日志高速输出导致后端丢弃了若干批次
- **THEN** 查看器中出现形如「跳过 N 行」的标记行，样式与普通日志行可区分

#### Scenario: 有界缓冲

- **WHEN** 日志持续高速输出数分钟
- **THEN** 查看器内存占用保持有界（保留最近内容，最旧行被丢弃），页面
  不因日志累积而明显变慢

#### Scenario: 翻阅时高流量不拉回

- **WHEN** 用户向上滚动翻阅历史且程序持续高速输出
- **THEN** 视口保持在用户翻阅位置附近，不被自动滚动打断（与既有跟随
  行为一致：让位于浏览）

### Requirement: App 移除控制

App 概况 SHALL 提供整个 app 的移除操作，调用 Web App 移除端点。该操作 MUST 经确认步骤后才发送请求，确认内容 SHALL 表明会删除注册、`app_dir` 内生成的配置会一并删除而外部部署配置保留，并明确不会自动停止存活程序。界面 MUST NOT 以先 stop 再 remove 的组合请求伪装成独立移除。

移除结果 SHALL 以可见反馈呈现：409 时显示阻塞程序及状态和先停止的提示，保留当前 app 与导航；成功后该 app 及其程序 SHALL 从侧栏与概况中消失，若正在查看该 app 则导航到仍可用的概况，不得继续显示可交互的陈旧控制项。成功反馈 SHALL 表明无需再执行 apply。

#### Scenario: 移除运行应用需先停止

- **WHEN** 用户对含 running 程序的 app 点击移除并确认
- **THEN** 界面显示后端返回的冲突原因及先停止提示，app 仍运行且保留在导航中，未代为执行 stop 或 apply

#### Scenario: 取消移除无副作用

- **WHEN** 用户点击移除后在确认步骤取消
- **THEN** 不发出移除请求，程序、注册与当前页面均不变

#### Scenario: 停止后从 Web 一步移除

- **WHEN** 用户在 app 全部程序停止后确认移除
- **THEN** 界面提示移除成功且无需 apply，侧栏与主区不再提供该已删除 app 的陈旧操作，若原页面选中该 app 则切换至可用概况

### Requirement: 全局程序总览

控制台 SHALL 在总览路由（`/`）展示覆盖全部应用的**程序总表**，按应用分组呈现该应用声明的
全部程序及其状态、重启计数、uptime、CPU、内存与日志速率；故障与退避中的程序 SHALL 在
所属分组内优先呈现或以警示样式醒目，使「谁挂了」无需逐级下钻即可看到。总览 MUST NOT
重复侧栏已承担的应用目录卡片列表。选中表格行 SHALL 进入对应程序详情。

#### Scenario: 一次看到全部程序

- **WHEN** 注册了 3 个应用、共 11 个程序且控制台加载完成
- **THEN** 总览按应用分组列出全部 11 个程序，分组标题含应用名与程序数

#### Scenario: 故障程序无需下钻可见

- **WHEN** 某程序处于 fatal 或 backoff
- **THEN** 总览对应行以警示样式与中文状态词呈现，分组内该行排在其他正常行之前或带可感知标记

#### Scenario: 行跳转详情

- **WHEN** 用户点击总览中某程序行
- **THEN** 主区切换到该程序的详情页

### Requirement: 列表行快捷操作

总览与 App 概况的程序行 SHALL 在鼠标悬停或键盘聚焦时，于行尾显现 ⋯ 触发按钮；点击 ⋯
或在行上右键 SHALL 打开统一「程序操作菜单」（语义见「程序操作菜单」），菜单项与当前
状态匹配（运行中提供 停止/重启，非运行且允许启动时提供 启动）。快捷操作区 MUST NOT
在悬停时推开或挤压同行其他列；行内 MUST NOT 再渲染常驻的 start/stop/restart 按钮组。
破坏性操作 MUST 经菜单内联确认后生效；操作结果 MUST 有可见反馈。

#### Scenario: 悬停出现操作

- **WHEN** 用户把指针移到运行中程序行上
- **THEN** 行尾出现 ⋯ 触发按钮，其他列位置不移动；点击后菜单提供 停止 与 重启

#### Scenario: 键盘可操作

- **WHEN** 用户用 Tab 聚焦到程序行的 ⋯ 按钮并触发
- **THEN** 菜单打开且可经键盘完成选中与确认，与鼠标路径一致

#### Scenario: 快捷操作失败有反馈

- **WHEN** 行内发起的 stop 请求被后端拒绝
- **THEN** 界面展示失败原因，不静默无反应

### Requirement: 品牌位版本号与关于对话框

控制台 SHALL 在左侧品牌位应用名下方以小号灰字显示当前守护进程的版本号（形如 `v0.1.0`），
与现有品牌小字同级；窄屏（≤720px）侧栏收为顶部条时 MAY 隐藏该行。品牌位 SHALL 是
控制台内版本号的唯一常驻展示位：页面级守护进程概况条 MUST NOT 再重复展示版本号。
用户双击版本号时 SHALL 打开「关于 appkeeper」对话框，展示版本号与构建元数据
（git 提交、构建时间、目标平台、Rust 版本），以及当前守护进程的控制端点、配置来源、
运行时长、应用数与程序数。对话框 MUST 可通过关闭按钮或 Esc 退出；版本位 MUST 可通过
键盘（Enter/Space）等价触发，且带可访问名称说明其用途。守护进程尚未提供投影时，
版本位 SHALL 显示占位符，对话框 SHALL 说明当前未连接，MUST NOT 渲染错误或空白字段。

#### Scenario: 侧栏显示版本号

- **WHEN** 控制台已连接守护进程且投影含版本 `0.1.0`
- **THEN** 品牌位应用名下方显示 `v0.1.0`，样式为小号灰字且不改变品牌行高

#### Scenario: 概况条不重复版本号

- **WHEN** 控制台已连接守护进程并渲染守护进程概况条
- **THEN** 概况条展示配置来源、运行时长、巡检、系统 CPU/内存与刷新控件，不含版本号；
  版本号只出现在品牌位

#### Scenario: 双击查看构建信息

- **WHEN** 用户双击品牌位版本号
- **THEN** 弹出对话框，显示版本号、git 提交、构建时间、目标平台、Rust 版本，以及控制端点、
  配置来源、运行时长与应用/程序数

#### Scenario: 键盘与关闭

- **WHEN** 用户用 Tab 聚焦版本号并按 Enter（或 Space），随后按 Esc
- **THEN** 对话框打开且焦点进入对话框；按 Esc 后对话框关闭且焦点回到版本位

#### Scenario: 离线占位

- **WHEN** 控制台从未取得守护进程投影
- **THEN** 版本位显示占位符，双击后对话框说明当前未连接，不显示伪造的版本或构建信息

### Requirement: 程序操作菜单

控制台 SHALL 以单一「程序操作菜单」承载程序的 start / stop / restart 操作，供进程详情
与列表行两处复用（见「单程序控制」「列表行快捷操作」）。菜单 SHALL 满足：

- **双入口**：在程序行或进程详情页上右键，或点击 ⋯ 触发按钮（含键盘 Menu 键 / 触屏点按），
  打开同一菜单；MUST NOT 存在只属于某一入口的菜单项。
- **菜单项与状态匹配**：运行中（running/starting）提供 停止 / 重启，stopping 等过渡态
  不提供任何操作，其余状态提供 启动；菜单项 MUST 按当前状态启用/隐藏。
- **动作配色**：菜单项与内联确认按钮带动作色（启动绿 / 重启琥珀 / 停止红），色值用途边界
  见 `webui-visual-system`「操作动作的配色语义」。
- **二次确认**：启动为无损操作，选中即执行；停止 / 重启选中后 SHALL 在同一浮层内联变形为
  确认步骤（含程序名与带动作色的确认按钮），确认后才生效；取消或 Esc / 点击浮层外
  MUST 关闭确认且不产生任何状态变更。MUST NOT 使用浏览器系统弹窗。
- **可访问性**：菜单 MUST 可键盘操作（打开、方向键移动、Enter 触发、Esc 关闭并归还焦点），
  菜单项带可访问名称；打开期间菜单项按 `data-kind`（start/stop/restart）暴露给测试。
- **反馈**：操作结果 MUST 以可见反馈呈现（成功 / 失败原因），与操作入口表面无关。

#### Scenario: 右键与 ⋯ 打开同一菜单

- **WHEN** 用户分别通过右键程序行与点击行尾 ⋯ 按钮打开菜单
- **THEN** 两次呈现的是同一份菜单内容与状态（同一组件），菜单项集合由程序当前状态决定

#### Scenario: 启动免确认直接执行

- **WHEN** 用户在停止状态的程序菜单中选中「启动」
- **THEN** 菜单关闭、启动请求立即提交，不出现确认步骤

#### Scenario: 停止需内联确认

- **WHEN** 用户在菜单中选中「停止」
- **THEN** 同一浮层变形为「确认停止 <程序名>？」并呈现取消与带红色的确认按钮；点确认才提交，
  点取消 / Esc / 浮层外点击则关闭且程序状态不变

#### Scenario: 键盘完成整个操作

- **WHEN** 用户用键盘聚焦 ⋯ 触发按钮（或在行上按 Menu 键）、Enter 打开菜单、方向键选中
  「重启」、Enter 进入确认、再 Enter 确认
- **THEN** 重启请求提交，全程无需鼠标；Esc 在任一步关闭菜单并归还焦点

#### Scenario: 菜单操作失败有反馈

- **WHEN** 菜单发起的 stop 请求被后端拒绝
- **THEN** 界面展示失败原因，而不是静默无反应
